# Real-S3 broadcast join CPU comparison

Only fuseBroadcastJoins changes between the measured arms. Hold the PR revision, service launch arguments, fact leaf fan-out (one), phase, table files, two worker hosts, four intermediate join workers, separate broker, S3 endpoint/region, independent answer oracle and load generator constant. The primary statistic is the sum of CPU seconds used by the two Pinot server processes during all work, divided by the number of fully validated queries, times 1,000. Both servers' operator execution, dispatch, garbage collection, and any processing in worker JVM threads are included. Mountpoint, broker, load driver and other processes are outside that numerator. Report Mountpoint CPU separately when measured. No idle baseline subtraction.

Set one P90 threshold of 1,000 ms before pilots. Use explicit scheduled arrivals with persistent per-thread HTTP connections, no query retries, no query-result cache, and strictly validate all count/sum groups against the fixture generator. Count response latency from scheduled arrival through receipt of the entire HTTP response, even if the driver queues it. CPU accounting extends through the full scheduled interval or final validated response, whichever is later. Record pending responses at the end of the scheduled interval and retain all individual sample timings. The driver captures CPU boundaries using concurrent private meter requests to the two workers and retains each measurement’s RTT, monotonic timestamp and process identity.

For steady-state selection, start low and double a shared offered rate until one arm exceeds P90, has wrong/failed requests, reaches a driver or drain guard, or reaches the declared ceiling. Freeze the highest passing common tested rate (a reproducible comparison point, not a capacity maximum). If a held-out measured confirmation fails, retain its results and repeat the *entire* balanced campaign at the next lower passing candidate. Pilots and warmups never enter reported results. Both members of a pair must deliver 100% correct answers, P90 ≤1,000 ms, P99 driver launch lag <20 ms, achieved QPS ≥98% of the shared offered rate and an inter-arm rate difference ≤2% of the offered rate. Report actual separate P90 values; the target is a common ceiling.

Use four pairs in the within-pair orders off/on, on/off, on/off, off/on. Use ≥45s and ≥128 timed requests per arm/window for the warm campaign. Use source-object GET and byte deltas and fixture identities to verify comparable I/O state. Split hot-cache and forced-cold/object-read results; never relabel setup-time S3 loading as query-time S3 reads. For repeated forced-cold measurements, evict during the idle interval before each scheduled request and require a positive data-object GET/bytes delta per query (plus matching cold-page residency where available). Preserve a failed or unclassifiable arm as an observation rather than reporting it as a scored source-read comparison.

Per pair: divide each arm's observed total worker CPU-s by its exact completion count, and report the percentage change of on vs off. Across matched pairs, sum worker CPU time and completions before normalization and report individual pairs, ranges and actual achieved rates/P90. Multiple windows on one host set are repeat measurements; no general fleet-wide claim. Record worker/broker EC2 shape and allocation while both arms use the identical infrastructure.

Forced-cold supplementary rate selection is fixed to 0.25, 0.5, 1, 2 and 4 offered QPS, advancing only if both arms pass the preceding rung. Each pilot includes at least eight timed, fully validated queries per arm. The scored forced-cold rate uses four pairs of ≥32 queries per arm and ≥20 seconds per arm. For every request, both hosts’ source fixture files must report zero resident pages after reset. Source GET/byte counters must settle before dispatch, rise through the request, and settle again before the next reset. The complete CPU interval includes idle spacing and garbage collection, providing the server budget at the actual sparse offered rate. Also retain per-query active-interval server CPU as a diagnostic. The warm suite uses 4, 8, 16, 32, 64 and 128 QPS with ≥16 requests and ≥8s per pilot/arm. All within-pair SLO and rate gates apply to both regimes.
